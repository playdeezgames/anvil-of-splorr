## Status and commands

The maintainer tracks open work as tasks in [coxswain](https://github.com/playdeezgames/coxswain-of-splorr) (project `anvil`); there is no TASKS.md or BACKLOG.md, and references below to task numbers are to that board. A fork does not need it.

A suite of editors behind one main menu, sharing two tool-agnostic frontends (native SDL2, web/wasm). Tools so far: `palette_editor`, `image_editor`, `tileset_editor`, `world_editor`, `glyph_editor`, `font_editor`, `controls_editor` and `gamepad_tester`.

- `common/`: palette model and JSON file format (strict: exactly 16 `{r,g,b}` entries, integers 0..255), `Renderer` interface (frontends implement `clear`/`fill_rect`/`present` on a 320x180 logical surface), the UI font (`common/font.odin`, drawn from the user's `default-font.json`), `input.odin` (the eight `Action` commands and the `Input_Event` union), `input_map.odin` (the editable binding table, see below), `gamepad.odin` (`Pad_State` snapshots, standard-layout indices), and `tool.odin` (`Tool`: the proc table a frontend drives; optional file hooks).
- A tool package (`palette_editor/`, `gamepad_tester/`) holds state, event handling and drawing, and exports `tool(&state) -> cm.Tool`. Palette editor: `layout.odin` shares rects between drawing and mouse hit-testing; file IO is request/response through `Tool.take_save/wants_load/load`, performed by the frontend.
- `image_editor/`: edits one 4-bit-per-pixel `cm.Image4` (`common/image4.odin`, up to 64x64, every pixel a palette index 0..15; a fixed 64x64 store keeps pixels hidden by shrinking). File `image.json` = `{"width","height","bytes"}` with **two pixels per byte** (left pixel = high nibble; each row padded to `ceil(w/2)` bytes, odd widths leave a 0 low nibble that is ignored on read), rows top to bottom; the palette is *not* in the file. Colours come from the palette editor's saved `palette.json` via the read-only aux-file hook (default VGA palette if missing), so changing the palette recolours the image. Same shape and patterns as the glyph editor (`layout/editor/draw/tool`; red = back, blue = File, `enter` resets and loads, guarded exit/close, tiled 3x3 preview). Modes: Draw (d-pad moves; **green paints the current colour** — there is no toggle, paint with colour 0 to erase; yellow Setup; blue File; red menu), Setup (rows: **drawing colour first** so yellow + left/right + red is a quick colour change, then width, height, then the action rows run with green: Flip H/V, Rotate L/R/180, Frame, Fill, Flood fill, Replace colour, Clear; the colour wraps 0..15 and is not part of the saved image or "dirty"), Rect (placing a rectangle: the cursor is the second corner, green draws it in the current colour, red cancels) and File. Whole-image operations live in `common/image4.odin` (`image4_flip_*`, `image4_rotate_*` — a quarter turn swaps width and height and counts as a change even for a blank non-square image —, `image4_flood_fill` (4-connected, iterative), `image4_replace_color`, `image4_clear`) and rectangles in `common/shape.odin` (`Shape` = None/Frame/Fill, `shape_has_cell`, `image4_draw_shape`/`bitmap_draw_shape`, corners in any order, clamped). Mouse tools are *armed*: FRAME/FILL arm a rectangle (next drag, corner to corner), FLOOD/REPLACE arm a click tool (next click on a pixel), red or the button again disarms, one-shot; CLEAR and the transform buttons act at once. Buttons are in three columns (file / transforms / tools) beside the preview. Mouse: click/drag paints the current colour (a drag keeps its starting colour), **right click picks up the colour under the pointer** (canvas pixel or swatch), clicking a palette swatch chooses it, -/+ buttons resize, SAVE/LOAD/MENU. Drawing uses `cm.canvas_draw_image` (indexed colour) in `common/canvas.odin`.
- `glyph_editor/`: edits one 1-bit-per-pixel `cm.Bitmap` (`common/bitmap.odin`, up to 64x64, JSON file with the pixels packed into bytes (see below); the fixed 64x64 store keeps pixels hidden by shrinking so growing back restores them, and files hold only the visible region). Same shape as the palette editor (`layout/editor/draw/tool`), same patterns: red = back, blue = File mode, `enter` resets to a blank bitmap then requests a Load, guarded exit. Modes: Draw (d-pad moves the cursor, no wrap; green toggles; yellow -> Setup; blue -> File; red -> menu), Setup (up/down choose a row: width, height, foreground, background, then the action rows run with green: Invert, Flip H/V, Rotate L/R/180, Frame, Fill; colours wrap; red -> Draw), Rect (as in the image editor, but the rectangle sets its pixels to the *opposite of the pixel it started on* — start on a clear pixel to draw, on a lit one to erase; preview squares are yellow for draw, red for erase) and File. Same armed-tool mouse behaviour and three button columns as the image editor; INVERT acts at once (`bitmap_invert`). The right panel also shows a 3x3 tiled preview of the bitmap in the chosen foreground/background (scaled by a whole number to fit, clipped and flagged "CLIPPED" when it cannot fit) and a one-row palette strip (left click = foreground, right click = background). The colours come from the palette editor's *saved* `palette.json` through the read-only **aux file** hook (`Tool.aux_file_name/wants_aux_load/load_aux`, serviced by both frontends, silent if the file is missing, default VGA palette otherwise; web reads it from the same localStorage key the palette editor wrote). Foreground/background are preview state only: not saved with the image, not "dirty", reset on each open. Mouse: click/drag paints (drag paints the value the first click set), +/- buttons resize, SAVE/LOAD/MENU. Layout uses `cell_size`/`cell_at`/`cell_rect` (canvas) and `preview_scale`/`intersect` (preview) so one set of rects serves drawing and hit-testing at any size. The built-in 3x5 font in `common/font.odin` also has a type called `Glyph`; the image type is `Bitmap` to avoid the clash.
- `font_editor/`: edits a `cm.Pixel_Font` (`common/pixel_font.odin`): character codes 0..255, any subset present, **one height for the whole font, a width per glyph** (each glyph is a `Bitmap`, up to 64x64; hidden pixels survive removing a glyph or shrinking). Codes 32..127 are the "printable" set: the grid tints missing ones red and the panel shows a DEFINED n/96 count. File `font.json` (`{"height", "glyphs": {"65": {"width", "bytes": [...]}}}`, only present glyphs). **The Pixel_Font and the `Editor` are ~1 MB: create them as globals or with `new()`, initialise in place (`editor_init(&e)`, `pixel_font_reset`, `pixel_font_from_json(bytes, &dst)`), and never return/copy them by value (stack).** Modes: Pick (16x16 grid; left/right one char, up/down one row; green edits, creating the glyph if absent; yellow Setup; blue File; red menu), Edit (the shared canvas, `cm.canvas_draw`; red -> grid), Setup (rows: this glyph's width, the font's height, this glyph present yes/no, then the action rows Copy, Paste, Delete and Flip horizontal/vertical (this glyph only; no rotation in the font editor), run with green; Delete needs green twice and any other command cancels the prompt) and File; Setup/File return to where they were opened (`back`). Mouse: click a cell selects, again edits; paint/drag on the canvas; -/+ and YES/NO buttons; COPY/PASTE/DEL (DEL needs a second click) and FLIP H/V beside the width/height values; SAVE/LOAD/EDIT-GRID/MENU. Copy/paste uses an in-app clipboard bitmap (`Editor.clipboard`); `pixel_font_paste_glyph` fits it to the current font height, and pasting creates the glyph if absent. Present=NO hides a glyph but keeps its pixels, while Delete (`pixel_font_delete`) clears everything. A load always returns to the grid. The panel shows the glyph scaled, coverage, and a sample sentence rendered in the font being edited (absent glyphs take no space). `common/canvas.odin` (`cm.Rect`, `canvas_cell_*`, `canvas_draw`) is shared with the glyph editor.
- **Pixel storage in files** (`common/bitmap.odin`, used by both the glyph and font files): one bit per pixel, each pixel row padded to a whole number of bytes (`bitmap_row_bytes(w) = ceil(w/8)`), leftmost pixel in the top bit (0x80) of a row's first byte, padding bits 0 on write and ignored on read, rows top to bottom; `bitmap_pack`/`bitmap_unpack` do the conversion and the JSON field is `"bytes"` (a list of whole numbers 0..255, one pixel row per line). Old files with `"rows"` of `"#"`/`"."` strings are still read (`bitmap_read_pixels`) but never written. In memory a `Bitmap` is still a `[64][64]bool`.
- `default-font.json` (repo root) is the user's **hand-drawn** font and **the font every tool's own text is drawn with**: `common/font.odin` embeds it (`#load`), parses it on first use into a global `Pixel_Font` (thread-safe, ~1 MB, `ui_font()`), and `draw_text`/`text_width`/`font_has`/`text_is_drawable` use it. It is a pure cell grid: each glyph carries its own blank bottom row and blank right column, so there is **no extra spacing** anywhere: text advances by glyph width, lines by the font height; `GLYPH_H` (6) and `LINE_ADVANCE` (= `GLYPH_H`) are compile-time constants that a test checks against the file, so re-check every layout if the height changes. Characters the font lacks draw as a solid 3x5 block (so gaps show) and the tools' text tests fail on them; strings are drawn byte by byte (codes 0..255). The file is theirs like `input_map.json`: never regenerate, reset or overwrite it (the old built-in 3x5 font and its export tool are gone). `,` uses the bottom row and `~` uses the rightmost column, both on purpose (confirmed by the user): do not "fix" them or add tests that require blank edges. Edit it in the font editor by copying it to `font.json` (native) or putting it in browser storage under `anvil-of-splorr.font.json`, then copy the result back and rebuild.
- **Text entry** (`common/text_entry.odin`): the keypad for typing with only the eight commands, as the user specified: a 16x6 grid of characters (every printable ASCII once, grouped capitals / lower case / digits / punctuation; the very last cell is an inert filler) plus a row of four wide action cells BKSP, CLEAR, DONE, CANCEL. D-pad moves (wrapping; in the action row it steps cell to cell; vertical moves keep the column), green presses the highlighted cell, yellow = backspace and red = cancel anywhere, blue does nothing. Mouse: hover highlights, left click presses. A tool owns a `Text_Entry`: `text_entry_begin(&e, prompt, initial, max_len)` (max 32; `text_entry_begin_long` allows up to `TEXT_ENTRY_CAPACITY` = 1024 and the field then shows the end of the text led by `...`), send every event to `text_entry_handle` (returns Editing / Done / Cancelled), draw with `text_entry_draw(&e, r, labels)` instead of its own screen, read `text_entry_text(&e)` on Done. Max 32 characters. Note: the user's font draws lower case with the capital shapes, so the lower-case rows look the same as the capitals until real lower-case glyphs are drawn.
- `launcher/`: the main menu. A `Launcher` is itself a `cm.Tool`: it shows the menu, forwards events, pad snapshots, drawing and file hooks to the running tool, and returns to the menu when that tool's `take_exit` says so. **To add an editor:** write its package with `tool(&state)`, give it `enter` (called each time it opens; load its file there) and `take_exit` (set when the user backs out), and add an `Entry` in `apps/suite/app/app.odin`. Nothing in the frontends changes.
- `apps/<name>/app/app.odin` picks what a build contains: frontends `import "app:app"` and `build.sh` passes `-collection:app=apps/<name>`. `suite` (the default) is the menu plus every editor; `palette_editor`, `glyph_editor` and `gamepad_tester` build one tool standalone. `apps/<name>/title.txt` is the web page title.
- `frontends/sdl2/main.odin`: window, SDL scancode translation, game controller polling into `Pad_State` (controller API only: devices SDL has no standard mapping for are ignored), file IO in the working directory, named by the running tool (`cm.tool_file_name`; the launcher reports the active tool's name, so files are per tool, e.g. `palette.json`).
- `frontends/web/`: `web.odin` (`#+build js`; DOM events via `core:sys/wasm/js`, Gamepad API polled in `step`, drawing through `canvas_*` imports), `index.html` (2D-canvas shim; `@TITLE@`/`@TOOL@` filled by `build.sh`; the "Open file" button appears only if the tool has files). Files are per tool: Save = localStorage (key = file name) + download; Load = restore localStorage (works from a gamepad). The page's "Open file" button is shown only while the running tool has files.

Input model: tools never see keys or buttons. There are exactly eight commands (up, down, left, right, green, red, blue, yellow) plus mouse events. `input_map.json` (repo root is the single source: the web build symlinks it next to the page so a rebuild never clobbers edits, and native reads `./input_map.json`) maps gamepad standard-layout button indices (d-pad 12-15, red 0, green 1, yellow 8, blue 9 by default) and KeyboardEvent.code names (arrows, green Space, red Escape, yellow Tab, blue Enter by default) to commands. It is hand-editable: omitted commands keep defaults, `null` unbinds, `_`-prefixed keys are notes, and unknown commands/keys, out-of-range buttons or two commands on one input are errors (frontends report them and fall back to defaults). Key names are the shared vocabulary in `input_map.odin` (`LETTER_CODES`, `DIGIT_CODES`, `NAMED_CODES`); the SDL2 frontend's `key_code` must translate scancodes into those names. `input_map.json` also has a `labels` section: the on-screen name of each command (default = the command name, max 12 chars, `null`/empty = default). Tools get the live map via `Tool.set_input_map` and read labels with `cm.action_label` at draw time, so help text and the mode banner follow the file (the web build applies it a moment after start). New on-screen text that names a command must use `action_label`, never a hardcoded "GREEN". The committed `input_map.json` is the user's own, edited by hand, so don't reset it to defaults; a test only requires that it parses. Frontends resolve key presses with `action_for_key`, and `tool_update_pads` resolves pad button presses with `action_for_pad_button`; only standard-layout pads produce commands. There is no quit command: native quits by closing the window, web has no quit; "leaving" always means back to the main menu.

Palette editor modes (red always means back): Browse (d-pad moves between swatches, green -> Edit, yellow copies the selected colour and -> Paste, blue -> File, red -> main menu; with unsaved changes the first red only shows an "UNSAVED ... LEAVE ANYWAY" banner and any other command cancels it), Edit (left/right = -/+1, up/down = +/-16, green cycles R/G/B, blue -> File, red -> Browse), Paste (d-pad moves, green pastes the copied colour onto the selected swatch, repeatable, yellow re-copies the selected one, blue -> File, red -> Browse) and File (green saves, yellow loads, red/blue cancel; every choice returns to Browse). The mouse works in all modes (COPY, PASTE, SAVE, LOAD, MENU buttons) and switches mode itself: swatch click -> Browse (stays in Paste), slider click or wheel over a slider -> Edit. The clipboard is in-app only (`Editor.clipboard`). Help text and banner come from `help_lines`/`banner_text`, which tests check for width with the longest labels and for characters the font lacks (`cm.text_is_drawable`, against the UI font). Any new on-screen string should be covered the same way. Web file transfers use one static buffer (`FILE_CAP` in `frontends/web/web.odin`, 4 MiB by default, set by `WEB_FILE_MIB=<n> ./build.sh web`; the page asks the module via the exported `file_capacity()`, so nothing is mirrored): keep large buffers off the stack, and keep a worst-case font file (`test_largest_font_round_trips`) under it. A game's world can bypass it: embed with `#load` (see `anvil_runtime/world.odin`), or have the page fetch files from beside it and hand them to the tool (`WEB_FETCH=world.json`, a `<meta name="anvil-fetch">` in the built page, `loadFetched()` in `index.html`). Screenshots from the in-app browser pane can lag a step behind the real state (the pane only runs frames while visible): take two before judging. Closing the app with unsaved changes is guarded too: `Tool.allow_close` (editors answer false the first time, showing the same prompt; native window close calls it, and the web page asks the browser to confirm via `beforeunload` while `tool_is_dirty` is 1). Opening the editor (`enter`) resets to the default palette and reloads the saved file, so unsaved edits do not survive leaving (the glyph editor does the same).

The gamepad tester ignores pad commands on purpose (testing must not switch pads or leave) and shows raw `Pad_State` (click to switch pads); it leaves via the keyboard's red command (`Command.from_pad == false`) or its MENU button. Standalone builds have no menu, so exit requests are ignored there.

**Controls editor** (`controls_editor/`, menu entry CONTROLS): edits `input_map.json` in the app. It works on the *live* `Input_Map` the frontend gives it through `set_input_map` (a rebind applies at once), shows a table (command, key, pad button, label; last row RESET TO DEFAULTS) and rebinds by **raw capture**: green on a key or pad cell calls `begin_capture`, and while `Tool.wants_raw` is true the frontends hand every key press (`cm.Raw_Input`, SDL: `tool_raw` in `handle_sdl_event`, web: `handle_key`, which also prevents the default; the key is "" when it is outside the shared vocabulary) and every standard pad button press (`tool_update_pads`) to `Tool.handle_raw` *instead of* turning it into a command; the mouse is untouched, so the CANCEL button and an 8 second timeout (`Tool.update`) are the ways out. A key or button another command has is refused with a note naming it (unbind that one first), a pad press while a key is wanted (and the other way round) keeps waiting with a note. Yellow unbinds the cell (a label back to the command's name), a label is typed with the keypad (max 12, empty = default), RESET TO DEFAULTS needs a second green and, like every edit, a SAVE. Blue opens File (green saves, yellow loads the file again); red/MENU leave, asking first when the live map differs from what the file holds (`editor_dirty`). **Saving keeps the file's notes**: `cm.input_map_to_json_keeping(map, original_text)` writes the notes (`_` entries at the top and inside each section, sorted by name) back; the editor remembers the text of the file it loaded or wrote (up to 16 KiB). The file is `input_map.json` in the working directory natively; on the web SAVE stores it in browser storage and offers it as a download (the served file is what the page reads at start, so the download has to replace it). Opening the tool marks the live map as what the file holds and asks for the file again; a valid file becomes the live map. The editor is not in a game's app unless the game adds it (`ce.tool(&controls)`, see `apps/suite/app/app.odin`); the launcher menu's rows are 13 px apart now so eight entries fit above its help text.

Parity is enforced by tests (`test_every_*_by_each_input`): every swatch, channel, value 0..255, save and load must be reachable with the commands alone (keyboard and gamepad both produce them) and with the mouse alone. Exception: on web, opening a file is a page button (browser file dialog), so command-only users get Save/Load via localStorage instead.

**Sound plumbing** (`common/audio.odin`): a tool or game returns `Audio_Request`s (Play on a channel 0..3 with mono i16 samples at a rate and a loop flag, Stop, Stop_All) from the optional `Tool.take_audio` (one per call, the launcher forwards to the running tool); each frame the frontend calls `cm.tool_service_audio(&tool, &mixer)` and the `Mixer` (4 voices, copies the samples, sums and clips, resamples by position step, allocation-free `mixer_render`) is pulled by the audio device. SDL2: `open_audio` (22050 Hz mono S16, callback thread, main loop holds `LockAudioDevice` around service; no device = silent, never an error); web: `audio_fill`/`audio_buffer`/`audio_active` exports and an AudioWorklet in `index.html` (an inline Blob module that queues blocks the main thread renders on request through the worklet's message port, so no special headers; a ScriptProcessor is the fallback) created on the first key/click/touch (browsers refuse audio before a gesture; gamepad presses do not count, so a sound asked for before that is silent). `testdata/external_app` plays a jingle (green), loops a tune (blue) and stops (red) as the example.

**Presenting and gamepad hints.** The SDL2 frontend draws through `cm.Present_Guard` (`common/present_guard.odin`): a frame is presented once after `draw` unless the tool presented, so games need not call `renderer_present` (the editors still do; harmless). At start-up it prints `gamepads: SDL sees N, opened M ...` plus ignored devices and unreadable `/dev/input` files (`report_gamepads`, `input_device_access`, text in `common/gamepad_hints.odin`); `GAMES.md` explains the `input` group and mappings. `./build.sh check` also runs `odin test testdata/external_app/app -collection:anvil=$PWD`.

**Game clock and games' own apps.** `Tool.update(data, dt_ms: f64)` is optional (editors leave it nil); both frontends call `cm.tool_update(&tool, elapsed_ms)` once a frame before `draw` (SDL2: `sdl.GetTicks` difference; web: `step`'s `dt` seconds x 1000), which clamps to 0..`MAX_FRAME_MS` (100) and forwards; the launcher forwards it to the running tool only. A game outside this repo builds with `APP_DIR=<folder with app.odin> [APP_NAME=] [OUT_DIR=] ./build.sh native|web|run|serve`: `build.sh` links the folder into `build/ext/<name>/app` as the `app` collection, always passes `-collection:anvil=<this repo>` (games `import "anvil:common"` / `"anvil:anvil_runtime"`), and for the web page uses the game's own `title.txt`/`input_map.json`/`game_tags.json` (in `APP_DIR` or its parent) when present. Recipe in `GAMES.md`; `./build.sh check` builds `testdata/external_app/` both ways and checks that its `input_map.json` is the one linked.

## What this is

A suite of tools for making game assets, built to the user's own specs. All tools are written in **Odin** and each runs on two frontends:

- **Native**: SDL2 rendering (Odin's `vendor:sdl2`).
- **Web**: `js_wasm32` build with a browser frontend.

The first tool is a **palette editor**: a 16-entry palette whose entries each hold red, green and blue values in 0..255.

Hard requirement: **every function must be reachable by keyboard, mouse, or gamepad**. When adding a feature, wire up all three input methods.

## Architecture to preserve

Because one tool must run on two very different frontends, keep the tool logic out of the platform code:

- Tool state, input handling and drawing logic live in platform-independent Odin packages. They take abstract input events (keyboard / mouse / gamepad mapped to common actions) and emit draw calls against a small renderer interface (clear, fill rect, text/sprite).
- The SDL2 frontend and the wasm frontend each implement only that renderer interface and translate native events into the common input events. Neither contains tool logic.
- Shared code across tools (renderer interface, input mapping, widgets, palette/file formats) belongs in a common package, not duplicated per tool.

## Game-side runtime (`anvil_runtime/`)

What a game imports to use a world (it is not `runtime/`: Odin reserves that package name). `anvil_runtime` depends only on `common`, builds for native and `js_wasm32` (`./build.sh check` checks both) and has no platform code.
- `world.odin`: `new_world`/`reset_world`, `load(w, bytes)` (readable error, `w` untouched on failure), `find_tag`, `find_map`, `missing_tags`, `terrain_at`, `cell_has_tag`, `cell_is_solid` (effective `solid`; outside the map counts as solid), `cells_with_tag`, `player`, `character_type/_sprite/_image/_has_tag`, `authored_location`, palette/tile/map sizes. A `World` is ~35 MB: a global or `new()`.
- `play.odin`: `Play_State` (about 0.9 MB, mostly the inventories' entries: a global or `new()`): every character's current map and cell, copied from the authored placements by `play_init`. A game changes only this, never the loaded world: `play_position`, `play_character_at`, `play_characters_in_map`, `play_can_step`/`play_step` (refused by edges, solid cells and other characters; a game lets the player walk onto a pickup by `play_unplace`-ing it first), `play_place`, `play_unplace`. Features have positions in the `Play_State` too (`play_feature_position/_at`, `play_features_in_map`, `play_place_feature`, `play_unplace_feature`; a feature always blocks: `Move_Result.Feature`, characters are refused a feature cell with `Place_Result.Feature_There`; `draw_features` before `draw_characters`; as-authored queries `feature_count/_type/_sprite/_image/_has_tag/_at`, `authored_feature_location`, `features_with_tag`). **Collisions:** `play_step` queues a `Collision` (mover character, `kind` Character/Feature, `other` index, map, target cell, step dx,dy) whenever a step is refused by another character or a feature (not for walls or edges, not for `play_can_step`); the game drains them with `play_take_collision` (oldest first), `play_clear_collisions`; the queue holds `MAX_COLLISIONS` (64), dropping the oldest and counting `collisions_lost`; `play_init` empties it.
- Items at run time (`anvil_runtime/items.odin`, design in `WORLD.md`): `Owner` (`owner_character/_feature/_cell`, a character or feature index or a map cell), `Play_Entry {slot, item_type, count, overrides}` in the `Play_State`'s pool of `WORLD_MAX_ENTRIES` (8192) copied from the authored inventories by `play_init`. Authored queries: `item_type_count/find_item_type/item_type/_max_stack/_sprite/_image/_has_tag`, `item_prop_index/_default`. Changes: `play_add_item` (merges into matching stacks, never beyond max stack, returns what did not fit and an `Add_Result`; nothing is left behind if nothing fit), `play_remove_item`, `play_transfer` (one entry at a time, moves only what fits, keeps overrides), `play_transfer_all`, `play_drop`, `play_split`, `play_merge`, `play_set_entry_value` (a value equal to the default clears the override), `play_clear_items`; reads `play_entry_count/_entry/_entry_value`, `play_cell_has_items`, `play_cells_with_items`. An emptied inventory is gone. **A step onto a cell that holds an inventory is never refused**: `play_step` queues a `Contact` (`play_take_contact`, `play_clear_contacts`, 64, oldest dropped, `contacts_lost`). `draw_inventories` (first entry's sprite, before `draw_features`). Do not copy a `Play_State` onto the stack (0.9 MB).
- Play mode (`world_editor/play.odin`, `Mode.Play`, YELLOW or the PLAY button in the hub): the first consumer of `anvil_runtime`: `Editor.play` is a `Play_State`, stepping uses `play_can_step`/`play_step` (solid cells, edges, other characters), drawing uses `zoom_window`/`draw_terrain`/`draw_characters` with a clip below an 11-pixel strip (banner, last message, BACK). `play_zoom` picks the largest whole zoom (1..8) at which the map fits, else the window follows the player. Leaving just drops the state, so the world is untouched; the mouse clicks a neighbouring cell.
- Game parameters (`common/world_params.odin`): `World.params` (up to 64 `Param`: name, `kind` Number/Text, `number` clamped to 32 bits, `text` up to 32 chars; both values are kept when the kind is toggled), `world_add/duplicate/delete/rename_param`, `world_set_param_number/_text`, `world_param_number/_text(name, default)`; `params` in the file is optional on load. The world editor's Params section is a normal list; opening an item shows the value screen (`world_editor/params.odin`, `Mode.Value`): the keypad types a number or text via `Editor.text_target` (`Text_Target.Number/.Text_Value`; `.Name` is the list's rename), a bad number resumes the keypad with a note. The IMPORT button's place is IMPORT (tilesets), CREATE (tags) or KIND (params). The hub has two levels: the top lists three sections (LOOK = palette, tile size, tilesets, terrain sets, sprite sets; RULES = tags, params; ACTORS = character types, characters, maps) with one-line counts (RULES adds a red "N MISSING"); green opens a section (`Editor.hub_level`, `top`, `hub_section`, `section_rows`), red goes up one level (red at the top leaves, with the unsaved prompt), BLUE = file and YELLOW = play at both levels, left/right change the tile size only inside LOOK; mouse: click opens, the BACK button (`SECTION_BACK`) goes up, SAVE/LOAD/MENU/PLAY stay.
- Sounds (`common/world_sounds.odin`): `World.sounds` (up to 64 `Sound`: name, `text` up to 1024 printable ASCII characters held in a fixed buffer with `text_len`, `loop`), `world_add/duplicate/delete/rename_sound`, `world_set_sound_text` (refuses too long or non-printable; the empty text is fine, and PLAY validity is the parser's business), `world_set_sound_loop`; `sounds` is optional in the file. PLAY text is parsed by `common/play_text.odin` (`play_parse(text) -> []Play_Note, Play_Error, ok`: frequency, duration and sounding seconds, an error with its character position, 60 s cap; `play_duration`) and rendered by `common/square_synth.odin` (`play_render(notes) -> []i16` mono 22050 Hz square wave at a quarter of full scale, sample-exact timing; `wav_encode(samples) -> []u8`), all pure and tested. World editor (`world_editor/sound.odin`, `Mode.Sound`; `Section.Sounds`/`Hub_Row.Sounds` live in the RULES hub section): the Sounds list is a normal list; the sound screen plays through `Editor.audio_ops` (a small queue of Play/Stop that `editor_take_audio`, wired as `Tool.take_audio`, turns into `Audio_Request`s on channel 0, rendering at take time so the samples live on that frame's temp allocator), text is typed with `cm.text_entry_begin_long` (`Text_Target.Sound_Text`), `sound_status` gives the line under the name (length and notes, or the upper-cased parse error with `error_at` for the marked character), `wrap_text` wraps the text box (12 lines, `MORE...` when cut); leaving the screen, starting to type, or loading a world queues a Stop. Runtime (`anvil_runtime/sound.odin`): `find_sound`, `missing_sounds`, `broken_sounds`, `sound_loops/seconds/pcm`, `sound_play(world, name, channel) -> Audio_Request` (renders PLAY text to a Play request, looping per the sound), `sound_stop`, `sound_stop_all`; `testdata/external_app` uses them. 
- Game tags (`common/game_tags.odin`): `Game_Tags` (up to 64 names with optional 80-character notes) from a hand-edited `game_tags.json`; `game_tag_status` (Missing / Unused / Present), `game_tags_missing`, `world_create_missing_tags`. The world editor reads it through the aux-file hook: its `aux_file_name` now answers with whatever it has pending (`tileset.json` for an import, `game_tags.json` otherwise, `""` for nothing), `wants_aux_load` pops one request and `load_aux` knows which file it got (`Editor.aux_current`); the frontends poll the name *before* `wants_aux_load`. The Tags list shows needed tags as NEEDED / NEEDED, UNUSED / MISSING (missing ones are extra virtual rows past `tag_count`), CREATE reuses the IMPORT button's place, and renaming/deleting a needed tag needs a second green (`confirm_rename`, `confirm_delete` with a different banner). Web: the page fetches `game_tags.json` beside it into browser storage at start, and "Open file" with that name stores it; `./build.sh web` links a repo-root `game_tags.json` if there is one.
- Drawing (`common/world_draw.odin`, wrapped by `anvil_runtime/play.odin`): `World_Draw` = a window of a map (`col,row,cols,rows`), where its first cell goes (`x,y`), the cell size in pixels, a clip rect and the colour for missing pictures; `world_zoom_draw` makes one at a whole-number zoom of the tiles. `world_draw_terrain` and `world_draw_authored_characters` draw it, `world_draw_character` draws one character (without its sprite's transparent colour), `world_cell_rect`/`world_cell_at` map cells and pixels, and `clipped_renderer` wraps any Renderer so everything is clipped, never an error (cells outside the map, windows bigger than the map, windows off the surface). The map editor draws its canvas through these (cells scaled to any size, down-sampled when small), so editor and game cannot disagree; a game uses `zoom_window`/`draw_terrain`/`draw_characters` (the Play_State's positions, not the authored map).
- Loading was made linear in the number of placed characters (a lookup, not a scan of every cell per character), so a full world loads quickly.

## MCP server (`mcp_server/`, `anvil_mcp/`)

Plan and tool table: `MCP.md`. `mcp_server` is the testable core (`handle_message(&server, bytes) -> reply` for JSON-RPC 2.0; `Server` = one open ~35 MB `World` on the heap, `dirty`, the file it came from, the folder `--dir`); `anvil_mcp/main.odin` is only the stdio loop (one message per line, replies on stdout, 16 MiB line limit). Built with `./build.sh mcp` (`build/anvil_mcp`), checked/tested by `./build.sh check|test`. Tools are the `tools()` table in `tools.odin` (it joins `world_tools` / `rules_tools` / `look_tools` / `actor_tools` from `tools_world.odin`, `tools_rules.odin`, `tools_look.odin`, `tools_actors.odin`, `tools_features.odin` (`feature_type_*`, `feature_*` with place/unplace; `map_get` lists a window's features, `map_list`/`world_summary` count them, `render_map` draws them, `play_walk` reports `feature`), `tools_items.odin` (`item_type_*`, `item_prop_set/delete`, `inventory_list/get/add/remove/set/clear`; the owner is exactly one of `character`/`feature` id or `map`+`x`+`y`, entries are numbered from 0, `props` is an object of name to whole number; `map_get`/`map_list`/`world_summary` report cell inventories, `render_map` draws them (`items: false` omits), `play_walk` reports `items_at`), `tools_render.odin`, `tools_sound.odin`, once, thread-safely; shared helpers `need_world`, `changed` (sets `dirty`), `arg_*`, `find_*` are in `tools.odin`/`tools_look.odin`; every editing tool starts with `need_world` and names things, never indexes, and the model's own `world_*` procs enforce the rules) (name, description, JSON schema text, proc returning a `Tool_Result`); a refusal is `fail(text)` (MCP `isError`), never a crash. Rules: file names are relative to the folder, no `..`/absolute/backslash, end in `.json`; nothing reaches disk before `world_save`; replacing unsaved work needs `discard: true`; saving over another existing file needs `overwrite: true`. Pieces 1 and 2 have the world file tools, tags, parameters, palette, tile size, tilesets and images (pixels as rows of hex digits), terrain sets/terrains and sprite sets/sprites; piece 3 adds maps (rows of symbols from `TERRAIN_SYMBOLS` + legend, paint/fill/flood/replace, per-cell tags), character types, characters (ids are uuids, an 8-digit prefix works if unique), the player, and `play_walk` (the runtime's `play_step` on a throwaway `Play_State`); piece 4 adds `render_map/tile/sprite/palette`: a `Tool_Result.png` is sent as an MCP image content (base64), pictures are drawn by the editors' own `world_draw_*`/`canvas_draw_thumbnail` into a `cm.Rgb_Canvas` (`common/rgb_canvas.odin`, a Renderer over a picture of any size) and written by `cm.png_encode_rgb` (`common/png_write.odin`: uncompressed stored deflate, indexed when <=256 colours, tested by decoding with `core:image/png`); renders are capped at 1024 pixels a side (auto zoom aims for 512). `./build.sh install-mcp` puts sound tools (`sound_list/check/new/set/delete/get/render/export`; `Tool_Result.wav` is sent as MCP `audio` content, text with a parse error is refused with its character position, inline renders are capped at 30 s and `sound_export` writes a .wav file); a stable "prod" copy in `~/.local/bin/anvil_mcp` (version = git revision, `--version`; worlds in `~/anvil-worlds`) so development does not disturb other sessions' servers. `MCP_TOOLS.md` is generated (`build/anvil_mcp --tools > MCP_TOOLS.md`; a test fails when it is stale, so regenerate it after changing any tool). `tools()` allocates with the default allocator on purpose (a test's tracking allocator would be freed under the other tests). Tests use temp folders under `/tmp` and run from the repo root; `smoke_test.odin` builds a whole game world through tool calls.

## Tileset editor notes

- `common/tileset.odin` holds the model (<=256 named Image4s sharing one width/height, names unique printable ASCII <=32) and JSON; `Tileset` is ~1 MB: use `new()`/globals, never copy by value. The web `FILE_CAP` (web.odin) is 4 MiB by default to fit the largest tileset; `WEB_FILE_MIB` raises it.
- `tileset_editor` modes: Pick (thumbnail grid), Edit (embeds the real `image_editor` via `editor_begin_embedded`, size locked, quarter turns refused unless square, image written back after every event), Setup (rows Rename..Height), File, Text (the `cm.Text_Entry` keypad; refused names resume it with a note).
- Palette comes from `palette.json` via the aux-file hooks.

## World editor notes

Spec: `WORLD.md`. A world is one tile size, one palette, up to 16 named tilesets, up to 16 named terrain sets (each up to 256 terrains with a default, a solid flag and a tileset + image reference **by name**) and up to 64 named maps (1..64 square, cells are terrain indexes in the map's set, written to the file as names via a per-map table).

- `common/world.odin` is the model and `world.json` format. `World` is ~35 MB: a global or `new()`, never copied by value. All reference upkeep lives there (`world_rename_tileset/_image/_terrain_set`, `world_delete_*` returning how many things use it, `world_map_change_set` remapping cells by name and refusing if a terrain is missing, `world_map_set_size` filling new cells with the set's default). `common/world_map.odin` has the whole-map operations (flips, square-only rotation, flood, replace, clear, shapes).
- Sprite sets (`common/world_sprites.odin`, `sprite_editor`): sprites are a tile reference by name plus a transparent colour index (`SPRITE_NO_TRANSPARENT` = -1 for none; `canvas_draw_thumbnail(..., transparent)` skips it, `canvas_draw_checker` is the backdrop); the editor can show a world terrain behind them (view state only). The `sprite_sets` list is optional in `world.json`. Tileset/image use counts (`world_tileset_uses`, `world_image_uses`) include sprites; `uses_text` words the refusal.
- Tags (`common/world_tags.odin`, `common/tag_list.odin`): a world list `tags` (tag 0 = "solid", reserved) and u64 masks in the entities: `Terrain.tags`, `Character_Type.tags` (types: has / has not), `Character.tags_set/tags_cleared` and `World_Map.cell_tags` (instances: inherit / set / cleared; effective value via `world_character_has_tag` / `world_cell_has_tag`). `world_delete_tag` closes the gap in every mask. `Tag_List` + `tag_list_draw` is the shared window every Tags screen uses (terrain, character type, character, map editors have `Mode.Tags`); the old terrain `solid` bool is gone (legacy `"solid": true` loads as the tag). Flips/rotations/shrinks carry a cell's own tags.
- Characters (`common/world_characters.odin`): one world table keyed by `Uuid` ([16]u8, random v4 from `world_new_uuid`, a splitmix64 generator seeded from the clock in `editor_enter`, kept across loads); map cells (`World_Map.characters`, a Uuid per cell) and `World.player` refer by uuid; character types (name + sprite set/sprite by name) are protected like terrains' tilesets (`world_char_type_uses`, sprite and sprite set deletes refuse while a type draws them). `world_place_character` moves, refuses taken cells; map flips/rotations carry characters (`world_map.odin`), `world_map_set_size` refuses to cut one off. Editors: `character_type_editor`, `character_editor` (hub rows CHARACTER TYPES / CHARACTERS) and the map editor's Characters layer (`map_editor/characters.odin`; `Layer` switch, its own Setup rows via `row_offered`).
- Features (`common/world_features.odin`): `Feature_Type` (name, sprite, tags; up to 64) and `Feature` (uuid, name label, type by name, tags_set/cleared; up to 2048) in `World.feature_types/features`, a `World_Map.features` Uuid grid (adds about 4 MB to a World), the same helpers as characters (`world_add/duplicate/delete/rename_feature(_type)`, `world_place_feature`/`world_unplace_feature`/`world_feature_at`/`world_feature_location`, `world_feature_has_tag`, `world_cycle_feature_tag`). One shared rule: a cell never holds a feature and a character (`Place_Result.Feature_There` for a character refused, `.Character_There` for a feature refused; `read_features` rejects files with both); `world_map_shrink_blocked` counts features too; flips/rotations carry the grid; `world_duplicate_map` clears the copy's characters and features (it used to copy the characters grid, which put a character in two cells); uuids come from one generator and avoid both tables; sprite protection and renames cover feature types. File sections are written before `characters` (which ends the file). Editors: `feature_type_editor` and `feature_editor` are copies of the character type editor and the character editor (no player) hosted by the world editor (`Mode.Feature_Type`/`.Feature`, hub rows FEATURE TYPES / FEATURES in ACTORS; the top summary of ACTORS reads `N CHARACTERS  N FEATURES  N ITEM TYPES  N MAPS`); `world_draw_feature` is the shared drawing of one feature. The map editor's third layer (`map_editor/features.odin`, `Layer.Features`; `toggle_layer` cycles the layers (terrain, characters, features, items); Setup rows `Feature`, `Feat_Type`, `Feat_Rename`, `Feat_New`, `Feat_Unplace`, `Feat_Delete`; buttons reuse the Characters layer's places, so the terrain layer's turn-button dimming now applies to the terrain layer only) places, picks and edits features, and `world_draw_authored_features` draws them between terrain and characters. The runtime is in `anvil_runtime` and the MCP tools in `mcp_server/tools_features.odin`. 'Used by' notes on sprite deletes now say `USED BY n TYPE(S)` since feature types count too.
- Properties of character/feature types (`common/world_props.odin`, task #63 of project `anvil`): `Character_Type.props` and `Feature_Type.props` are `Prop_Set`s (the same as item types'), `Character.overrides` and `Feature.overrides` are `Prop_Overrides` (index-based, equal-to-default dropped). `world_char_type_add_prop/_delete_prop` and `world_feature_type_add_prop/_delete_prop` (delete shifts the overrides of everything of that type), `world_character_value/_set_value`, `world_feature_value/_set_value`; `world_set_character_type`/`world_set_feature_type` clear the overrides when the type changes. File: `"props"` on types (a list, written only when the type has some) and on characters/features (an object of the values that differ), read through the same `read_prop_set`/`read_prop_overrides` as item types. Editors: PROPS screens in `character_type_editor`/`feature_type_editor` (a patched copy of the item type editor's: `Mode.Props`, `Text_Target`, the PROPS button next to TAGS) and in `character_editor`/`feature_editor` (`Mode.Props`, values per instance, `Setup_Row.Props`; the feature editor's buttons were re-spaced to fit PROPS next to TAGS, the character editor's PROPS sits left of BACK). Runtime: `anvil_runtime/props.odin` (`character_prop_index/_default/_value`, `feature_*`; `Play_State.character_values/feature_values` copied by `play_init`, `play_character_value`/`play_set_character_value`/`play_feature_value`/`play_set_feature_value`; the Play_State is about 1.1 MB). MCP: `char_type_prop_set/delete`, `feature_type_prop_set/delete` (`set_prop_tool` shared with `item_prop_set`), `props` on `character_new/edit` and `feature_new/edit` (`parse_props_arg` validates before anything changes), props shown in the type and instance lists. The demo `world.json` has hardness (tree), locked (door) and weight (rock) with a few feature values.
- Items (`common/world_items.odin`, `common/prop_set.odin`, design in `WORLD.md`; coxswain task #1 of project `anvil` has the decisions): `Item_Type` (name, sprite, tags, `max_stack` 1..1e9, `props: Prop_Set`; up to 128), `Entry {inventory uuid, type name, count, overrides: Prop_Overrides}` in one world pool (`World.entries`, 8192, entries of one inventory keep their order) and `Inventory {uuid}` (`World.inventories`, 1024; 256 entries each). The owner holds the uuid (`Character.inventory`, `Feature.inventory`, `World_Map.inventories` grid, about 4 MB); `Inventory_Owner` (`owner_cell/_character/_feature`), `world_owner_inventory/_entry/_entry_count/_add/_remove/_clear_inventory`, `world_inventory_owner` (finds the owner by scan), `world_delete_inventory`, `world_inventory_tidy` (an inventory with no entries goes: **never leave one empty**), `world_entry_value/_set_value` (an override equal to the default is dropped by `prop_override_set`, so equal values mean equal overrides), `world_entries_mergeable`. `world_owner_add` merges into matching stacks first and returns what did not fit with an `Add_Result`. Upkeep: item type delete refused while entries use it (`world_item_type_uses`), `world_set_item_type_max_stack` returns how many entries are bigger and changes nothing, deleting a property shifts the entries' overrides (`world_item_type_delete_prop`), sprite/sprite set protection and renames and tag deletes cover item types, deleting a character/feature/map deletes what it held, duplicates hold nothing, `world_map_shrink_blocked` counts cells with inventories, flips/rotations carry the grid. File: `item_types` and `inventories` (the owner is written on the inventory, as `{"kind": "cell"|"character"|"feature", ...}`); a reader refuses an empty inventory, a missing owner and an owner with two. `Prop_Set` (names + defaults, up to 16) is reused by character types and feature types (next bullet). Editors: `item_type_editor` (a copy of the feature type editor plus a STACK row and a PROPS screen; hub row ITEM TYPES in ACTORS, `Mode.Item_Type`) and `inventory_editor` (`Mode.Inventory`, `open_inventory(e, owner, back)` in the world editor; opened from the ITEMS button of `character_editor`/`feature_editor` (they set `items_requested`, the character editor's buttons were re-spaced) and from the map editor's fourth layer `Layer.Items` (`map_editor/items.odin`, `items_requested`, `cursor_owner`; Setup rows `Cell_Open`, `Cell_Clear`; no Tags row there; `toggle_layer` cycles four layers)). Drawing order everywhere: terrain, cell inventories (`world_draw_authored_inventories`, first entry's sprite via `world_draw_item_type`), features, characters. A `Contact` queue and the inventory operations are in `anvil_runtime/items.odin` (see above) and the MCP tools in `mcp_server/tools_items.odin`. The demo `world.json` has three item types (gold, sword with damage/durability, potion) and two cell inventories (three entries), plus three feature types (tree, door, rock; all `solid`, the door also has a `door` tag) and five features placed on its map; it has no player.
- Triggers (`common/world_triggers.odin`, design in coxswain task #64 of project `anvil`, documented in `WORLD.md`/`GAMES.md`): `Trigger_Type` (name, sprite, tags, `props`; up to 64) and `Trigger` (uuid, name, type, tags set/cleared, `overrides`; up to 2048) in `World.trigger_types/triggers`; a trigger is in no place, in a map cell (`map_name` by name, x, y) or on a feature, and many may share one (`world_add_trigger`, `world_place_trigger`, `world_unplace_trigger`, `world_triggers_in_cell`, `world_set_trigger_type`, `world_rename/delete_trigger`). Editors: `trigger_type_editor` and `trigger_editor` (hub rows in ACTORS) and the map editor's fifth layer (`map_editor/triggers.odin`, `Layer.Triggers`, last in the `toggle_layer` cycle; Setup rows Trigger/Trig_Type/Trig_Here/Trig_Rename/Trig_New/Trig_Unplace/Trig_Delete; no tags). Runtime (`anvil_runtime/triggers.odin`): `play_step` queues `Triggered` (Entered / Bumped with a `Bump_Reason`; `play_take_triggered`, 64, `triggered_lost`), places and values live in the `Play_State`, `draw_triggers` goes after terrain and before inventories. MCP: `mcp_server/tools_triggers.odin`. The Anvil only notifies; the game decides what a trap does. Draw order everywhere: terrain, triggers, inventories, features, characters.
- Packages: `map_editor`, `terrain_editor` and `sprite_editor` (hosted only, edit the world in place, no files), `world_editor` (the tool: Hub, List, Setup (actions), Text, File, and the embedded Palette / Tileset / Terrain / Map modes). The palette editor and tileset editor got an *embedded* mode (`editor_begin_embedded`): no File mode, red leaves with no prompt, SAVE/LOAD hidden, MENU reads BACK; embedded tileset editor locks the tile size to the world's, refuses deleting an image a terrain uses and updates terrains when an image is renamed. The world editor copies a tileset in and back out (~1 MB) and edits the others in place.
- New and Duplicate (in the tileset editor, and the world editor's lists) ask for the name with the keypad first, then open the item's editor.
- The world editor Editor is over 35 MB (global in the apps). Web builds use `-o:minimal` (4 s instead of ~12 min); `WEB_OPT=speed ./build.sh web` restores the optimised build.
- Huge-world editing in the browser has no size cap beyond `FILE_CAP`; the game case is settled (see `FILE_CAP` in `frontends/web/web.odin`).

## Odin toolchain notes

Use the Odin release pinned as `ODIN_VERSION` in `.github/workflows/ci.yml` (`odin` on the `PATH`). The wasm approach, shared with the maintainer's other projects:

- Target `js_wasm32` with Odin's own runtime `core/sys/wasm/js/odin.js` (no emscripten): `odin build <pkg> -target:js_wasm32 -out:<dir>/<name>.wasm`, then copy `$(odin root)/core/sys/wasm/js/odin.js` next to it. The page calls `odin.runWasm(...)`.
- The wasm module exports a `step` proc that `odin.js` calls every animation frame; event callbacks must set `context = ctx` (saved in `main`) before using anything context-dependent.
- Draw via a **2D canvas** through `foreign import` procs implemented in the JS page, not WebGL (WebGL was tried and dropped in prior projects).
- The `.wasm` must be served over http (e.g. `python3 -m http.server`), not opened from `file://`.
