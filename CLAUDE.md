# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Status and commands

A suite of editors behind one main menu, sharing two tool-agnostic frontends (native SDL2, web/wasm). Tools so far: `palette_editor`, `glyph_editor`, `font_editor` and `gamepad_tester`.

- `common/`: palette model and JSON file format (strict: exactly 16 `{r,g,b}` entries, integers 0..255), `Renderer` interface (frontends implement `clear`/`fill_rect`/`present` on a 320x180 logical surface), built-in 3x5 font, `input.odin` (the eight `Action` commands and the `Input_Event` union), `input_map.odin` (the editable binding table, see below), `gamepad.odin` (`Pad_State` snapshots, standard-layout indices), and `tool.odin` (`Tool`: the proc table a frontend drives; optional file hooks).
- A tool package (`palette_editor/`, `gamepad_tester/`) holds state, event handling and drawing, and exports `tool(&state) -> cm.Tool`. Palette editor: `layout.odin` shares rects between drawing and mouse hit-testing; file IO is request/response through `Tool.take_save/wants_load/load`, performed by the frontend.
- `glyph_editor/`: edits one 1-bit-per-pixel `cm.Bitmap` (`common/bitmap.odin`, up to 64x64, JSON file of `"#"`/`"."` rows; the fixed 64x64 store keeps pixels hidden by shrinking so growing back restores them, and files hold only the visible region). Same shape as the palette editor (`layout/editor/draw/tool`), same patterns: red = back, blue = File mode, `enter` resets to a blank bitmap then requests a Load, guarded exit. Modes: Draw (d-pad moves the cursor, no wrap; green toggles; yellow -> Setup; blue -> File; red -> menu), Setup (up/down choose a setting: width, height, foreground, background; left/right change it; colours wrap; red -> Draw) and File. The right panel also shows a 3x3 tiled preview of the bitmap in the chosen foreground/background (scaled by a whole number to fit, clipped and flagged "CLIPPED" when it cannot fit) and a one-row palette strip (left click = foreground, right click = background). The colours come from the palette editor's *saved* `palette.json` through the read-only **aux file** hook (`Tool.aux_file_name/wants_aux_load/load_aux`, serviced by both frontends, silent if the file is missing, default VGA palette otherwise; web reads it from the same localStorage key the palette editor wrote). Foreground/background are preview state only: not saved with the image, not "dirty", reset on each open. Mouse: click/drag paints (drag paints the value the first click set), +/- buttons resize, SAVE/LOAD/MENU. Layout uses `cell_size`/`cell_at`/`cell_rect` (canvas) and `preview_scale`/`intersect` (preview) so one set of rects serves drawing and hit-testing at any size. The built-in 3x5 font in `common/font.odin` also has a type called `Glyph`; the image type is `Bitmap` to avoid the clash.
- `font_editor/`: edits a `cm.Pixel_Font` (`common/pixel_font.odin`): character codes 0..255, any subset present, **one height for the whole font, a width per glyph** (each glyph is a `Bitmap`, up to 64x64; hidden pixels survive removing a glyph or shrinking). Codes 32..127 are the "printable" set: the grid tints missing ones red and the panel shows a DEFINED n/96 count. File `font.json` (`{"height", "glyphs": {"65": {"width", "rows": [...]}}}`, only present glyphs). **The Pixel_Font and the `Editor` are ~1 MB: create them as globals or with `new()`, initialise in place (`editor_init(&e)`, `pixel_font_reset`, `pixel_font_from_json(bytes, &dst)`), and never return/copy them by value (stack).** Modes: Pick (16x16 grid; left/right one char, up/down one row; green edits, creating the glyph if absent; yellow Setup; blue File; red menu), Edit (the shared canvas, `cm.canvas_draw`; red -> grid), Setup (rows: this glyph's width, the font's height, this glyph present yes/no, then the action rows Copy, Paste and Delete, run with green; Delete needs green twice and any other command cancels the prompt) and File; Setup/File return to where they were opened (`back`). Mouse: click a cell selects, again edits; paint/drag on the canvas; -/+ and YES/NO buttons; COPY/PASTE/DEL (DEL needs a second click); SAVE/LOAD/EDIT-GRID/MENU. Copy/paste uses an in-app clipboard bitmap (`Editor.clipboard`); `pixel_font_paste_glyph` fits it to the current font height, and pasting creates the glyph if absent. Present=NO hides a glyph but keeps its pixels, while Delete (`pixel_font_delete`) clears everything. A load always returns to the grid. The panel shows the glyph scaled, coverage, and a sample sentence rendered in the font being edited (absent glyphs take no space). `common/canvas.odin` (`cm.Rect`, `canvas_cell_*`, `canvas_draw`) is shared with the glyph editor.
- `launcher/`: the main menu. A `Launcher` is itself a `cm.Tool`: it shows the menu, forwards events, pad snapshots, drawing and file hooks to the running tool, and returns to the menu when that tool's `take_exit` says so. **To add an editor:** write its package with `tool(&state)`, give it `enter` (called each time it opens; load its file there) and `take_exit` (set when the user backs out), and add an `Entry` in `apps/suite/app/app.odin`. Nothing in the frontends changes.
- `apps/<name>/app/app.odin` picks what a build contains: frontends `import "app:app"` and `build.sh` passes `-collection:app=apps/<name>`. `suite` (the default) is the menu plus every editor; `palette_editor`, `glyph_editor` and `gamepad_tester` build one tool standalone. `apps/<name>/title.txt` is the web page title.
- `frontends/sdl2/main.odin`: window, SDL scancode translation, game controller polling into `Pad_State` (controller API only: devices SDL has no standard mapping for are ignored), file IO in the working directory, named by the running tool (`cm.tool_file_name`; the launcher reports the active tool's name, so files are per tool, e.g. `palette.json`).
- `frontends/web/`: `web.odin` (`#+build js`; DOM events via `core:sys/wasm/js`, Gamepad API polled in `step`, drawing through `canvas_*` imports), `index.html` (2D-canvas shim; `@TITLE@`/`@TOOL@` filled by `build.sh`; the "Open file" button appears only if the tool has files). Files are per tool: Save = localStorage (key = file name) + download; Load = restore localStorage (works from a gamepad). The page's "Open file" button is shown only while the running tool has files.

Input model: tools never see keys or buttons. There are exactly eight commands (up, down, left, right, green, red, blue, yellow) plus mouse events. `input_map.json` (repo root is the single source: the web build symlinks it next to the page so a rebuild never clobbers edits, and native reads `./input_map.json`) maps gamepad standard-layout button indices (d-pad 12-15, red 0, green 1, yellow 8, blue 9 by default) and KeyboardEvent.code names (arrows, green Space, red Escape, yellow Tab, blue Enter by default) to commands. It is hand-editable: omitted commands keep defaults, `null` unbinds, `_`-prefixed keys are notes, and unknown commands/keys, out-of-range buttons or two commands on one input are errors (frontends report them and fall back to defaults). Key names are the shared vocabulary in `input_map.odin` (`LETTER_CODES`, `DIGIT_CODES`, `NAMED_CODES`); the SDL2 frontend's `key_code` must translate scancodes into those names. `input_map.json` also has a `labels` section: the on-screen name of each command (default = the command name, max 12 chars, `null`/empty = default). Tools get the live map via `Tool.set_input_map` and read labels with `cm.action_label` at draw time, so help text and the mode banner follow the file (the web build applies it a moment after start). New on-screen text that names a command must use `action_label`, never a hardcoded "GREEN". The committed `input_map.json` is the user's own, edited by hand, so don't reset it to defaults; a test only requires that it parses. Frontends resolve key presses with `action_for_key`, and `tool_update_pads` resolves pad button presses with `action_for_pad_button`; only standard-layout pads produce commands. There is no quit command: native quits by closing the window, web has no quit; "leaving" always means back to the main menu.

Palette editor modes (red always means back): Browse (d-pad moves between swatches, green -> Edit, yellow copies the selected colour and -> Paste, blue -> File, red -> main menu; with unsaved changes the first red only shows an "UNSAVED ... LEAVE ANYWAY" banner and any other command cancels it), Edit (left/right = -/+1, up/down = +/-16, green cycles R/G/B, blue -> File, red -> Browse), Paste (d-pad moves, green pastes the copied colour onto the selected swatch, repeatable, yellow re-copies the selected one, blue -> File, red -> Browse) and File (green saves, yellow loads, red/blue cancel; every choice returns to Browse). The mouse works in all modes (COPY, PASTE, SAVE, LOAD, MENU buttons) and switches mode itself: swatch click -> Browse (stays in Paste), slider click or wheel over a slider -> Edit. The clipboard is in-app only (`Editor.clipboard`). Help text and banner come from `help_lines`/`banner_text`, which tests check for width with the longest labels and for characters the font lacks (`cm.text_is_drawable`: the 3x5 font has no `;`, `@`, `~` etc., which would draw as a box; note the digit 0 looks identical to the fallback box, so `font_has` is an explicit list, not a glyph comparison). Any new on-screen string should be covered the same way. Web file transfers use one static 2 MB buffer (`FILE_CAP` in `frontends/web/web.odin`, mirrored in `index.html`): keep large buffers off the stack, and keep a worst-case font file (`test_largest_font_round_trips`) under it. Screenshots from the in-app browser pane can lag a step behind the real state (the pane only runs frames while visible): take two before judging. Closing the app with unsaved changes is guarded too: `Tool.allow_close` (editors answer false the first time, showing the same prompt; native window close calls it, and the web page asks the browser to confirm via `beforeunload` while `tool_is_dirty` is 1). Opening the editor (`enter`) resets to the default palette and reloads the saved file, so unsaved edits do not survive leaving (the glyph editor does the same).

The gamepad tester ignores pad commands on purpose (testing must not switch pads or leave) and shows raw `Pad_State` (click to switch pads); it leaves via the keyboard's red command (`Command.from_pad == false`) or its MENU button. Standalone builds have no menu, so exit requests are ignored there.

Parity is enforced by tests (`test_every_*_by_each_input`): every swatch, channel, value 0..255, save and load must be reachable with the commands alone (keyboard and gamepad both produce them) and with the mouse alone. Exception: on web, opening a file is a page button (browser file dialog), so command-only users get Save/Load via localStorage instead.

```bash
./build.sh check                 # odin check every package, and both frontends for every tool
./build.sh test                  # odin test every package (default target)
./build.sh run [app]             # native build + run; app defaults to suite (the main menu)
./build.sh native|web [app]      # build/<app> or build/web/<app>/
./build.sh serve [app] [port]    # web + http.server, default :8000 (use a fresh port after rebuilding: the browser caches app.wasm)

```

SDL2 dev headers and libs are installed, so `vendor:sdl2` links. Every `*_test.odin` needs `#+build !js` or the wasm build fails on `core:testing`/`core:os`. Unit tests do not cover the SDL2 or JS glue; to eyeball layout without a window, render a tool's draw through a software SDL renderer to a BMP, or serve the web build and fake `navigator.getGamepads` from the browser console.

## What this is

A suite of tools for making game assets, built to the user's own specs. All tools are written in **Odin** and each runs on two frontends:

- **Native**: SDL2 rendering (Odin's `vendor:sdl2`).
- **Web**: `js_wasm32` build with a browser frontend.

The first tool is a **palette editor**: a 16-entry palette whose entries each hold red, green and blue values in 0..255.

Hard requirement: **every function must be reachable by keyboard, mouse, or gamepad**. When adding a feature, wire up all three input methods.

## Architecture to preserve

Because one tool must run on two very different frontends, keep the tool logic out of the platform code:

- Tool state, input handling and drawing logic live in platform-independent Odin packages. They take abstract input events (keyboard / mouse / gamepad mapped to common actions) and emit draw calls against a small renderer interface (clear, fill rect, text/sprite).
- The SDL2 frontend and the wasm frontend each implement only that renderer interface and translate native events into the common input events. Neither contains tool logic.
- Shared code across tools (renderer interface, input mapping, widgets, palette/file formats) belongs in a common package, not duplicated per tool.

## Odin toolchain notes

Odin is installed at `/home/yermom/.local/bin/odin`. The user's other repos (see `/home/yermom/git/bok-of-splorr/splorr/Tech/Odin wasm recipe.md` and `Gotchas.md`, the shared knowledge vault for their SPLORR!! projects) establish the wasm approach to reuse here:

- Target `js_wasm32` with Odin's own runtime `core/sys/wasm/js/odin.js` (no emscripten): `odin build <pkg> -target:js_wasm32 -out:<dir>/<name>.wasm`, then copy `$(odin root)/core/sys/wasm/js/odin.js` next to it. The page calls `odin.runWasm(...)`.
- The wasm module exports a `step` proc that `odin.js` calls every animation frame; event callbacks must set `context = ctx` (saved in `main`) before using anything context-dependent.
- Draw via a **2D canvas** through `foreign import` procs implemented in the JS page, not WebGL (WebGL was tried and dropped in prior projects).
- The `.wasm` must be served over http (e.g. `python3 -m http.server`), not opened from `file://`.

Read those two vault notes before building the wasm frontend; do not edit the vault from this repo unless asked.
